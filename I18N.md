**How the i18n library works** (`scripts/i18n.js`)

- The project uses a tiny in-repo i18n micro-library exposed as `window.i18n`.
- Initialization: `i18n.init({ defaultLang = 'en', path = '/locales' })` — returns `i18n.ready` (a Promise) and loads `locales/{lang}.json`.
    - **Language precedence**: Query parameter (`?lang=en` or `?lang=bn`) > localStorage > default language.
    - This allows users to open links with a specific language baked in, while still supporting persistent language preference via localStorage.
- `i18n.setLang(lang)` lets the app load a different locale at runtime and re-apply translations.
    - Automatically updates the browser URL with the language query parameter (e.g., `?lang=bn`), making it easy to copy and share URLs.
    - Also saves the language preference to localStorage for persistence across sessions.
- After loading translations `i18n.apply()` is called automatically to replace DOM content and a `CustomEvent('i18n-ready', { detail: { lang } })` is dispatched.
- The library binds `window.t` and `window.tx` so they are safe to call from other scripts even if translations haven't finished loading yet.
- The runtime also exposes a small helper, `createTransientElement(htmlStr, ...i18nArgs)`, that safely renders HTML templates (positional or printf-style) into a `DocumentFragment` using the same `tx`/`t` resolution logic. Use this helper when you need to insert HTML fragments produced from translations rather than calling `innerHTML` directly.

**Query parameter-based language selection**

- **URL-based language**: Visit `http://localhost:5500?lang=bn` to load the site in Bengali, or `?lang=en` for English. Query parameter takes precedence over stored preferences.
- **Dynamic URL updates**: When users click language buttons, the URL updates automatically (using `window.history.replaceState`) to include the language parameter. This makes it easy to copy, share, and bookmark language-specific links.
- **Example workflow**:
    1. User visits site normally → uses localStorage or default language.
    2. User clicks "🇧🇩 BN" button → language changes, URL updates to `?lang=bn`.
    3. User copies URL and shares it → recipient receives page already in Bengali, without needing to click buttons.
- **Implementation details**:
    - `i18n.getQueryParamLanguage()` — checks URL for `lang` parameter.
    - `i18n.updateURL(lang)` — updates browser history with the language query parameter.
    - Both functions are called during `init()` and `setLang()` to ensure URL and language state stay in sync.

**API: `t(key, vars)`**

- Example: `t('toasts.saved_scenario', { name: 'Acme' })` where locale contains `"toasts.saved_scenario": "Saved scenario: {{name}}"`.
  **API: `t(key, vars)`**
- Basic lookup: `t('some.key')` returns the translation value or the key if not found (fallback behaviour).
- Interpolation: `t` supports both `{{var}}` and `{var}` styles.
    - Example: `t('toasts.saved_scenario', { name: 'Acme' })` where locale contains `"toasts.saved_scenario": "Saved scenario: {{name}}"`.
- If `t` is called with an unknown key it returns the key string. Note: repository-level extraction/validation scripts were removed; add a validator in CI if you require enforcement.

**API: `tx(keyOrString, ...args)`**

- Example: `tx('pricing.session_with_percent', t('pricing.foundation'), '20%')` with locale `"pricing.session_with_percent": "%1$s (%2$s)"` => `"Foundation (20%)"`.
  **API: `tx(keyOrString, ...args)`**
- Positional / printf-style helper.
- If `keyOrString` exists in translations it's used as a template; otherwise the string itself is used as template.
- Supports numbered placeholders: `%1$s`, `%2$d`, etc and sequential `%s`, `%d`, `%f`.
    - Example: `tx('pricing.session_with_percent', t('pricing.foundation'), '20%')` with locale `"pricing.session_with_percent": "%1$s (%2$s)"` => `"Foundation (20%)"`.

**DOM integration: data attributes**
**DOM integration: data attributes**

- `data-i18n="key"` — sets element `textContent` (or `alt` on `img`) to `t(key)`.
- `data-i18n-html="key"` — sets `innerHTML` to the translation (used for safe HTML fragments that come from locales and are intentionally HTML). The runtime still supports `data-i18n-html`, but prefer using `createTransientElement()` programmatically when building elements in JS so HTML parsing is centralized.
- `data-i18n-placeholder="key"` — sets element `placeholder` to `t(key)`.
- `data-i18n-title="key"` — sets element `title` to `t(key)`.
- `data-i18n-aria="key"` — sets element `aria-label` to `t(key)`.
- `i18n.apply(root)` scans the DOM starting at `root` (defaults to `document`) and applies translations.

**Interpolation & types**
**HTML translations**

- Use `data-i18n-html` for safe HTML fragments and `tiers.services_html.N` keys are intentionally HTML — be careful with any untrusted data inside these translations.
- Naming convention: HTML-bearing translation values in the repo already follow a `_html` suffix (e.g. `model_assumptions.max_daily_revenue_html`, `labels.days_parenthetical_html`) or the `.services_html.N` pattern. Keep this convention: keys that contain tags should clearly indicate they are HTML (ending in `_html` or similar) so maintainers know when `innerHTML`-style insertion is expected.
- Prefer programmatic insertion using `createTransientElement()` in JS code instead of scattered `innerHTML` assignments; `createTransientElement()` centralizes resolution (`t`/`tx`) and parsing.
- `tx` uses positional/printf style: `%s`, `%1$s`, `%2$d`, etc. This is useful for translated strings that expect ordered substitutions or include formatting tokens.
